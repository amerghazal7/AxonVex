# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `docs/v1_release_plan.md` — audited v1.0 release plan: defect inventory (C1–C24), workstream table, phased milestones, quality gates.
- Project rules: `CLAUDE.md` and `.cursor/rules` (graphify-first codebase navigation, project conventions).
- Regression tests for C4, C16, and C17.
- Regression test for C18 (re-entrant health-check callback registration must not deadlock).
- Regression tests for C1 (all ready tasks execute each scheduler cycle; removing a task mid-execution is safe).
- Regression tests for C2 (`SafetyManager` e-stop halts the system; hook registration/clearing).
- Concurrent stress regression test for C3 (8-thread allocate/deallocate ownership stamping; TSan-clean).
- Regression tests for C12 (a handler may mutate the policy registry during dispatch, call `evaluateAll()` or `triggerEmergencyStop()` re-entrantly; a policy may query the manager from `evaluate()`; the evaluation period may change while the loop runs).
- Regression tests for C14 (`logf`/`LOGF_*` substitute their `{}` placeholders in order, leave unmatched placeholders literal, ignore extra arguments; `LOGF_CRITICAL` compiles and logs exactly once).

- Sanitizer builds: `-DAXONVEX_SANITIZER=address|thread|undefined` on the root `CMakeLists.txt`, wired to a 3-way `sanitizers` matrix job in CI. Quarantined tests (throughput asserts, two known races) are listed with reasons in the workflow.

- Hostname and IPv6 support for the TCP and UDP transports. Both resolved addresses with `inet_pton(AF_INET, ...)`, which accepts a numeric IPv4 literal and nothing else — `"localhost"` and every other hostname failed, and IPv6 was unreachable. Both now resolve through `getaddrinfo` (new shared `interfaces/detail/addressResolver.hpp`), try the returned candidates in the system's preference order, and — for UDP — pick a destination matching the bound socket's family (C24).

### Changed

- `AxonVexSystem::setSafetyManager`/`getSafetyManager` (never functional — the pointer was stored and never read) replaced by `setSafetyHook`/`getSafetyHook` on the new core-owned `core::SafetyHook` interface; `safety::SafetyManager` implements it. Core no longer names any safety-layer type.
- `updateSystemConfiguration` is now rejected once initialization begins (returns `false`) — worker threads read the configuration unlocked, and a live update was a data race that never re-applied to running components anyway (C25).
- `Logger`'s class doc comment no longer claims `<500ns per log entry` or "no dynamic allocation during logging": `logf`/`log` build `std::string`s per call (via `LogMessage`'s string members and, for `logf`, `formatString`), so they are not RT-safe and are not a fixed-latency operation. Reworded to state the true cost and point at the RT-path rule (C14).
- `PluginManager::loadPluginsFromDirectory()` now clears `lastError_` on entry, so its no-loader / `opendir()`-failure / empty-directory early-return paths no longer leak a stale error string left over from a previous call (the accumulate-after-loop summary behavior for in-scan failures is unchanged).
- **Breaking:** `PrecisionTimer::getElapsedNanoseconds()` (and `getElapsedSeconds`/`getElapsedMilliseconds`/`getElapsedMicroseconds`, which delegate to it) no longer throw `std::runtime_error` when the timer has never been started — they return zero instead. A timing getter reachable from RT-adjacent paths must not throw (C19).
- **Breaking:** `PluginManager`'s POSIX loader now requires every plugin to export `extern "C" std::uint32_t axonvex_plugin_abi_version()` (new `AXONVEX_PLUGIN_ABI_VERSION` in `pluginInterface.hpp`, value 1) — checked via `dlsym`/call before `axonvex_create_plugin()` is ever reached. A plugin without it, or one reporting a different version, fails to load with a reason instead of loading and risking UB at the first virtual call against a stale `PluginInterface` layout (C13).
- **Breaking:** `MissionPipeline::abort()`/`restart()`/`pause()`/`resume()`/`reset()`, and the `onEnter()` dispatch inside `startPipeline()`, no longer run synchronously on the calling thread. Each now only enqueues (the existing `controlPort_` for the first four; a dedicated `pendingReset_` flag for `reset()`, which can't share `controlPort_` — see its doc comment) and takes effect at the next tick, dispatched from `processAsync()`'s drain on the scheduler thread only. `status()`/`currentElementName()` keep their synchronous-read signature but now reflect the most recently *drained* command, not the most recently issued one (whole-branch-review finding 1 — see the C22 row in `docs/v1_release_plan.md` for the race this closes).
- **Breaking (batch-6 review, item 1):** `MissionPipeline::startPipeline()`'s Idle->Executing flip is now deferred to the drain too, alongside `onEnter()` — previously the flip happened synchronously while `onEnter()` was deferred, so a `processSync()` (or a queued `reset()`) landing in the gap between them could call `execute()`/`onExit()` on an element that had never been entered. `status()`/`currentElementName()` now read `Idle` immediately after a successful `startPipeline()` call and only reflect `Executing` once a `processAsync()` has actually drained the pending start (an extension of the same "takes effect at the next tick" contract from the entry above, not a new one). Regression tests `StartPipelineDefersFlipSoExecuteNeverPrecedesEnter` and `ResetQueuedBeforeDrainDoesNotExitNeverEnteredElement` reproduce both pre-fix pairing violations. **Follow-up (task-2 review fix):** `reset()` now cancels a not-yet-drained pending start — `resetImpl()` clears `pendingStart_` as part of the same drain pass, before the `pendingStart_` check that follows it in `processAsync()`, so a `reset()` issued after `startPipeline()` but before either has drained wins and the pipeline does not self-start on the next tick (previously the pending start survived the reset and the pipeline entered `Executing` one tick later regardless). `ResetQueuedBeforeDrainDoesNotExitNeverEnteredElement`'s expectation flipped from `enterCount() == 1` to `enterCount() == 0` to match.

### Removed

- **Breaking:** `BasePort::setThreadSafe` and `ProcessingUnit::setPortsThreadSafe`. A port's thread-safety mode selects between a locked and an unlocked access discipline, so changing it while the port was in use let two threads take different disciplines to the same data — an atomic flag makes the read safe, not the switch (C31). Pass the mode when the port is created instead: the port constructors and `createInputPort`/`createOutputPort`/`createAsyncInputPort`/`createAsyncOutputPort` take a trailing `bool threadSafe = false`, and the mode is fixed for the port's lifetime.
- **Breaking:** `BasePort::setMemoryPoolSize` / `getMemoryPoolSize` and the per-port memory pool behind them. The pool only ever backed the lock-free read path removed in C29; the methods are deleted rather than kept as no-ops so callers fail to compile instead of silently configuring nothing. `MemoryPool` itself is unaffected and still used for system event allocation.
- `examples/memory_pool_ports_simple_example.cpp`, which demonstrated the removed path.
- **Breaking:** `AxonVexSystem::saveConfiguration`, `::exportDiagnostics`, `::collectGarbage`, `::registerRecoveryCallback` (declared, never defined — a link error if ever called) and `::initialize(const Configuration&)` (silently ignored its argument: logged a warning, forwarded to `initialize("")`, and returned `true` regardless) (C6). No callers existed anywhere in `src/`, `tests/`, or `examples/`. The now-unused `recoveryCallbacks_` member and `AxonVexSystem::RecoveryCallback` typedef are removed with them; `ErrorHandler`'s own `RecoveryCallback` type is unrelated and untouched.

### Fixed

- C13: the ROS2 plugin (`axonvex_ros2`) was an `INTERFACE` library whose three `extern "C" inline` factory functions lived in the header — no translation unit ever compiled them, so no `.so` was ever produced and nothing was `dlsym`-able; the plugin could not be loaded by the `PluginManager` it was written for. It is now a real `add_library(... SHARED)` target built from a single `src/ros2Plugin.cpp` TU with non-inline `extern "C"` definitions (`nm -D` confirms `axonvex_create_plugin`, `axonvex_destroy_plugin`, `axonvex_plugin_abi_version` all with `T` visibility). Separately, `PluginManager::loadPlugin`'s dup-name `plugins_.emplace(...)` silently discarded the new instance while returning `true` to the caller — the instance and its dlopen handle leaked (ASan/LSan-confirmed). It now checks `emplace`'s result and, on a duplicate name, shuts down, destroys, and `dlclose`s the rejected instance before returning `false`. `PluginManager::makePosixLoader` also now uses explicit `RTLD_NOW | RTLD_LOCAL` (was bare `RTLD_NOW`, leaving the scope implementation-defined), and a new `PluginManager::lastError()` reports why a load failed (no loader configured, load failure, ABI mismatch, or duplicate name) instead of a bare `false` for all four. Also closed in the same pass: `PluginManager` had no destructor, so a manager destroyed with plugins still loaded leaked every instance and handle regardless of the dup-name path; `~PluginManager()` now calls `unloadAllPlugins()`, and **Breaking:** the class is non-copyable (copying would double-`dlclose`/double-`delete` the same owned resources).
- C22: `MissionPipeline`'s `status_`/`currentElement_`/`elements_`/`transitions_`/`startElementName_` are now guarded by one non-recursive `stateMutex_` (was: mutated by `processSync()` on the scheduler thread and by the control API from any thread with no synchronization — TSan-confirmed data races). Every control method (`startPipeline`/`abort`/`restart`/`pause`/`resume`/`reset`) snapshots the affected `MissionElement*` and applies its state flip under the lock, then calls `onEnter`/`onExit`/`reset` (user code) with the lock released, so a hook that re-enters the control API cannot deadlock; `processSync()` never holds the lock across `execute()`/`onEnter()`/`onExit()`. **New validation behavior:** `startPipeline()` now validates the transition graph first — the start element and every `transitions_` from/to key must name an element added via `addElement()` — and fails fast (`status() == Failed`, dangling reference reported through `getLastError()`) instead of silently wedging at runtime on the first bad transition. `addElement()` now documents the non-owned, stable-reference ownership contract for the `MissionElement*` it stores. **Whole-branch-review finding 1:** the fix above still dispatched the hook itself (`onExit`/`reset`/`onEnter`) on the CALLING thread, which could run concurrently with `processSync()`'s unlocked `execute()` on the scheduler thread against the same `MissionElement` — TSan-reproduced (`onExit()` write racing `execute()` write). See the "Changed" section above for the enqueue-and-drain-on-the-scheduler-thread fix; new regression test `DirectAbortDoesNotRaceConcurrentTick` (TSan-reproduced pre-fix, clean post-fix). `ConcurrentControlAndTickAreRaceFree` and `HookReenteringControlApiDoesNotDeadlock` updated for the deferred semantics.
- `PluginManager::loadPluginsFromDirectory()`'s `lastError()` is now meaningful after a scan: every file that fails to load during the scan is accumulated into a `"filename: reason"` list joined with `"; "` and reported after the loop, instead of `loadPlugin()`'s per-file `lastError_` reset silently erasing an earlier failure when a later file (readdir order is unspecified) happened to load successfully.
- `PluginManager::loadPlugin()`'s call to a plugin's `initialize()` is now exception-safe: a throwing `initialize()` is caught (`lastError_ = "plugin initialize() threw"`, instance destroyed, handle closed) instead of propagating out and leaking the instance and dlopen handle — consistent with the existing `abiVersion()`/`create()` guards.
- `Path::setDefaultDir()` and `Path::resetDefaultDirs()` now call `ensureInitialized()` first, preventing initialization-order bugs where customizations made before the first Path object is constructed would be clobbered by the magic-static init.
- C2: a `SafetyManager` emergency stop now actually halts the system — `setSafetyHook` registers an emergency callback that performs an emergency shutdown. Teardown is safe from any thread: hook dispatch synchronizes with clearing (so destroying the system with a live hook cannot dangle), `emergencyShutdown`/`stop` serialize thread-handle teardown via a shutdown mutex, and self-join guards let the e-stop fire from a system thread.
- C25: `SystemEvent` string leaks eliminated (LSan-clean) — events are dropped once shutdown begins, the queue is drained back to the pool after the event thread joins, and `initialize()` drains before its component rebuild replaces the event pool (the pool destructor does not destruct live blocks).
- C3: `MemoryPool`'s lock-free free list is no longer ABA-vulnerable — the head is a tagged `{tag:32, index:32}` 64-bit atomic and every pop/push increments the tag, so a stale CAS can never install a stale `next` (the double-handout mechanism).
- C12: `SafetyManager` no longer holds `policiesMutex_` across user code — `evaluateAll()` snapshots the policy set (as `shared_ptr`, so a policy removed mid-cycle stays alive), then runs `evaluate()`, event dispatch, and `triggerEmergencyStop` unlocked; a policy or handler can now call back into the manager without deadlocking, including a re-entrant `evaluateAll()` (which returns the in-progress cycle's worst level instead of blocking or recursing). Handlers moved off the unsynchronized `core::Caller` to a mutex-guarded list with snapshot-then-dispatch, and `evaluationPeriod_` is atomic (the evaluation loop read it unlocked).
- C27: `MemoryPool`, `ThreadSafeQueue` and `RingBuffer` are cache-line aligned but were heap-allocated with plain `new`/`make_unique`, which in C++14 only guarantees 16-byte alignment — every instance was misaligned (undefined behaviour, and the false-sharing padding was not actually separating anything). They now allocate through `AXONVEX_ALIGNED_NEW`. UBSan went from 118 failing tests to zero.
- C28: `InputPort`, `OutputPort` and `AsyncInputPort` leaked the object still held in their memory pool at destruction — the pool frees its blocks without running `~T`, so any non-trivial payload leaked (LSan-confirmed).
- C11: a short `::send` on the TCP transport counted a truncated payload as a fully sent message. Sends now resume from the offset until the whole payload is written, and report how many bytes actually made it. **Breaking:** the newline-delimited framing that corrupted binary payloads containing `0x0A` is replaced by a magic (`0xAF 0x01`) + big-endian `u32` length-prefix wire format — a 6-byte header followed by exactly that many payload bytes, capped at 16 MiB per frame. `TcpClient::send` refuses an over-limit payload before touching the socket; `TcpClient::recvLoop` treats a bad magic or an over-limit length as a fatal, loudly-reported framing violation instead of dispatching garbage or splitting a payload at an embedded `0x0A`. Old newline-framing peers are incompatible. See `docs/v1_release_plan.md`'s C11 row for the regression tests.
- C32: registering a port callback after the port had started carrying traffic raced the dispatch path, which reads those callbacks without a lock; replacing a `std::function` mid-invocation is a use-after-free. Registration is now explicitly setup-only and throws `std::logic_error` if attempted late, instead of failing silently at runtime. Locking the dispatch path was rejected deliberately: it would run user callbacks under a port lock, and copying the callback out to avoid that would allocate on the port hot path.
- C33: two threads calling `stop()` on a transport at the same time could both reach the thread join, which is undefined behaviour. Start and stop are now serialized and idempotent.
- C33 (second shape): calling `stop()` from a message or error callback crashed the process. Those callbacks run on the transport's own receive thread, so the call made that thread join itself, which throws — and the exception escaped the thread, taking the process down with it. Shutdown now recognises the reentrant call and lets the receive loop unwind on its own, deferring the join.
- Destroying a running `TcpClient` or `UdpSocket` crashed the process: neither had a destructor, so the still-running receive thread was destroyed rather than stopped. Both now shut down cleanly on destruction.
- C24 (silent platform failure): on non-Linux builds both transports reported successful startup, spun a thread that did nothing, and counted "sent" bytes that never left the process. They now report the failure and return `false`.
- C26: a safety policy that threw from `evaluate()`, a watchdog handler that threw, or a throwing emergency-stop callback each killed the process outright — the exception escaped the safety subsystem's own worker thread. All four sites are now guarded. A throwing policy is reported as a `CRITICAL` safety violation through the normal event path rather than ignored: a policy that cannot report cannot vouch for the system. Evaluation continues with the remaining policies, and both loops keep running.
- Calling `stop()` on a `SafetyManager` or `Watchdog` from inside a policy or handler crashed the process, for the same reason it did on the transports: those callbacks run on the component's own worker thread, so the call made that thread join itself. Shutdown now recognises the reentrant call and defers the join. The transports' equivalent check was also corrected — it read the thread object while startup was still assigning it, and sat behind a lock that an external `stop()` holds while waiting to join. Two follow-on crashes in the same area are fixed too: destroying a `Watchdog` from its own handler terminated the process, and two threads shutting one of these components down simultaneously could both reach the thread join, which hangs.
- C34: a message or error handler that called back into the transport's own registration API deadlocked the transport permanently, because callbacks were invoked while the registration lock was held. Handlers now run with no lock held. Unregistering from another thread waits for any in-flight dispatch to finish, so a handler can never be torn down mid-call; unregistering from inside a handler returns immediately, and that handler may still be invoked for the rest of the dispatch already under way. This holds when several threads are dispatching at once, which a transport does routinely — sends report errors on the calling thread while the receive thread delivers messages.
- C35: a callback on a connected input port that touched the sending port's connection API deadlocked, because sends dispatched to connected ports with the connection lock held. Sends now dispatch from an immutable snapshot of the connection list with no lock held, and take no allocation to do it.
- C30: `AsyncOutputPort::write` checked whether the port had any connections without holding the lock that guards the connection list, so a concurrent `connect`/`disconnect` could reallocate the list mid-read. The check now runs under the lock — but in its own critical section, so the output callback still runs with no port lock held.
- C24 (transport shutdown race): `TcpClient::stop()` and `UdpSocket::stop()` closed the socket while the receive thread was still blocked reading from it, and `send()` used the descriptor with no synchronization at all. Because a closed descriptor number is immediately reusable, an in-flight read or send could land on an unrelated file. Shutdown now stops the receive thread first and closes the socket only afterwards, sends hold the socket for the duration of the call, and the per-transport counters are atomic. Receive calls time out every 100 ms so shutdown never has to interrupt a blocked read — that timeout is the upper bound on how long `stop()` takes.
- C21: `RingBuffer`'s ctor called `make_unique<T[]>` (which already value-initializes every element) and then placement-new'd `T{}` over the live result — placement-new ends an object's lifetime without running its destructor, so every slot was constructed twice and destroyed once, leaking the first object's resources for any non-trivial `T`. The placement-new loop is deleted. The class doc's generic "lock-free" claim is reworded to the honest single-producer/single-consumer contract (two concurrent writers can both load `write_index_` and both claim `buffer_[current_write]`), with a memory-ordering argument comment next to `write_index_`/`read_index_` — same argument shape as `ThreadSafeQueue`'s per-slot `sequence`. Regression test `RingBufferTest.ConstructionAndDestructionAreBalanced` (pre-fix: 32 constructions vs 16 destructions for a 16-element buffer); new SPSC stress test `RingBufferTest.SpscStressPreservesValueIntegrityAndOrder` (one producer/one consumer, 200k items, deadline-guarded) backs the lock-free claim per project rule 8.
- C29: reading a thread-safe port could return a value out of memory another thread had already recycled. The ports' lock-free "pooled" path published a pool block through an atomic pointer and freed the previous block immediately, with no scheme to know whether a reader was still inside it — a use-after-free, ASan-confirmed. The pooled path is removed; thread-safe ports now use only the mutex path that was already present alongside it.
- C4: `MemoryPool::isEmpty()`/`isFull()` bodies were swapped.
- C10: SIGPIPE protection (`MSG_NOSIGNAL`) on TCP/UDP sends — peer teardown no longer kills the process.
- C16: `optional<>` move semantics now match `std::optional` (moved-from source stays engaged).
- C17: UUID v4 version bits applied to the correct 64-bit half — generated strings are RFC-4122-compliant.
- C23: `nextPowerOf2` `value >> 32` undefined behavior on 32-bit `size_t` removed (all 3 copies).
- C1: the scheduler now executes every ready task each cycle (previously one per tick — with tick ≈ period, same-priority tasks starved entirely) and runs user code without holding `tasksMutex_`; `removeTask`/`removeAllTasks` defer pool deallocation while a task is mid-execution; `addTask`'s pool-exhaustion callback moved outside the lock.
- C18: user callbacks are no longer invoked while holding locks — `performHealthCheck` and the event loop snapshot callbacks under `callbacksMutex_` and dispatch outside it; the scheduler's task-error callback and `std::cerr` moved outside `statsMutex_`. Fixed the unsynchronized `lastHealth_` read in the monitoring loop (member deleted; loop keeps a local timer) — this was the root cause of the intermittent `HealthCheckCallbacks` segfault (dangling stack write over a return address). Note: the first periodic health check now fires one `healthCheckInterval` after monitoring starts instead of immediately.
- C5: `Configuration::applyUpdates` unlocked `config_mutex_` mid-merge to notify callbacks while a recursive merge lambda still held live `nlohmann::json` references into `config_data_` — a concurrent writer, or the callback itself, could destroy the referenced node and the merge resumed writing through it (ASan-confirmed heap-use-after-free). `notifyCallbacks` separately invoked user callbacks while holding `callbacks_mutex_`, so a callback calling `registerCallback`/`unregisterCallback` deadlocked the non-recursive mutex. Updates are now merged fully under the lock into a change list, then callbacks are notified afterwards with no lock held; `notifyCallbacks` snapshots matching callbacks and dispatches unlocked. `loadFromJson` is now public (it was already fully implemented).
- C7: `emergencyShutdown`/`reset` wrote `currentState_` directly, bypassing `transitionState` entirely — no validation, no `totalStateTransitions` count, and no STATE_CHANGE event; the transition table also only allowed `FATAL_ERROR` from `STOPPING`, so a validated e-stop from any other state would have been refused. `transitionState` now treats `FATAL_ERROR` as legal from every state, and both `emergencyShutdown` and `reset` route through it. `publishEvent` gained a null guard for `eventPool_`/`eventQueue_` (same style as `drainEventQueue`'s) — routing e-stop through the validated path means it now reaches `publishEvent` even on a never-initialized system, where those pools don't exist yet. `initialize()` no longer rebuilds every component a second time with an identical configuration — that rebuild was the reason `initialize()` needed a `drainEventQueue()` workaround for C25 in the first place.
- C8: `ProcessingUnit` move operations are now explicitly `= delete` instead of silently defined-as-deleted by the compiler. The header previously advertised movability with `ProcessingUnit(ProcessingUnit&&) = default` while owning two non-movable `std::mutex` members and while ports and the system held stable raw pointers to the unit — relocation would dangle all of them. The `= default` moves were always ill-formed and never functioned, so no existing code could move these objects; this is a breaking change only in the trivial sense of catching incorrect code that was already impossible to run. Regression tests lock in non-movability via `std::is_move_constructible` and `std::is_move_assignable` static_asserts, guarding against any future attempt to reintroduce it.
- C9: `connectToSystem`/`disconnectFromSystem` locked the two systems' `systemPortsMutex_` in argument order, so `a.connectToSystem(&b)` concurrent with `b.connectToSystem(&a)` acquired the pair in opposite orders — an AB/BA deadlock. A self-connection (`targetSystem == this`) locked the same non-recursive mutex twice — UB. New private `lockSystemPortsWith` acquires both mutexes via `std::lock` (deadlock-avoiding) for the cross-system case, and locks only once for a self-connection, which is now a supported operation. Both functions call it instead of the raw `lock_guard` pair.
- C37: `LogOutput::defaultFormat` called `std::strftime(..., std::localtime(&time_t))` — `std::localtime` writes into a single shared static buffer and is not reentrant, so two `AxonVexSystem`s' Logger background threads formatting messages concurrently raced on libc-internal state (TSan showed a `free()` inside `tzset_internal` in the window, not just a torn timestamp). Found by `AxonVexSystemTest.OpposingCrossSystemConnectsDoNotDeadlock` under TSan. Fixed with `localtime_r` (POSIX) / `localtime_s` (Windows, guarded by `#ifdef _WIN32`), both writing into a caller-owned `std::tm`.
- C38: `isShuttingDown_` was set by `stop()`/`emergencyShutdown()` but never cleared, so `reset()` followed by `initialize()` left the flag stale — the re-initialized system's event thread exited its loop immediately and `publishEvent` silently dropped every event, while the state machine reported a healthy `INITIALIZED`/`RUNNING` system. `initialize()` now clears `isShuttingDown_` immediately before starting the monitoring/event threads, as the flag's single owner (`reset()` deliberately does not also clear it).
- C39: `initialize()` assigned a fresh `std::thread` straight over `eventProcessingThread_`/`monitoringThread_` without checking whether the existing handle was still joinable — `~std::thread` on a joinable thread is `std::terminate`. Reachable via an e-stop initiated from an event callback (running on the event thread, whose self-join guard defers cleanup and leaves the handle set) followed by `reset()` + `initialize()`: `reset()`'s own `emergencyShutdown()` call can `try_lock`-fail against the still-in-flight event-thread teardown and return without joining, leaving the stale handle for the next `initialize()` — reproduced reliably as `std::terminate` before the fix. New private `AxonVexSystem::joinAndClearThreadHandle` joins (self-join guarded) and clears both thread handles immediately after `transitionState(INITIALIZING)` and before `initialize()`'s C38 flag writes — joining first, while the flags still reflect "shut down", keeps any stale thread's loop-exit condition guaranteed rather than letting a flag reset revive it and block the join indefinitely.
- C14: `Logger::formatString` was `return format;` — every `logf`/`LOGF_*` call silently dropped all of its arguments (the substituted message never appeared, just the raw `{}`-templated string). It now substitutes each `{}` in order via a new `Logger::formatImpl` recursion (extra `{}` with no argument stays literal; extra arguments with no `{}` are ignored). `LOGF_CRITICAL` expanded to two concatenated `logf` calls and failed to compile at any use site (nothing used it) — it now expands to exactly one `logf` call, like the other `LOGF_*` macros. Regression tests `LogfSubstitutesPlaceholdersInOrder`, `LogfLeavesUnmatchedPlaceholdersLiteral`, `LogfIgnoresExtraArguments`, `LogfCriticalMacroCompilesAndLogsOnce` (the last is itself the regression: it does not compile pre-fix).
- C19: `PrecisionTimer::addSample` evicted the oldest sample at capacity with `samples_.erase(samples_.begin())` — an O(n) shift of up to 10k elements under `samples_mutex_` on every measured execution. It now ring-writes over the oldest slot via a `sampleHead_` index (O(1)); the retained set (most recent `max_samples_`) is unchanged. `PrecisionTimer::ClockType` was `std::chrono::high_resolution_clock`, which the standard permits to be non-steady (`isClockSteady()` measurably returned `false` on this toolchain); it is now `std::chrono::steady_clock`, immune to wall-clock adjustments. See the Changed section above for the `getElapsedNanoseconds()` throw removal, part of the same fix. Regression tests `SampleEvictionKeepsMostRecentSamples`, `ElapsedGettersReturnZeroBeforeStart`, `ClockIsSteady`.
- C39 follow-up hardening (whole-branch review): the `joinAndClearThreadHandle` calls in `initialize()` moved from mid-function to the top, above `initializeComponents()` — a stale thread from the same C39 lifecycle could still be running inside `emergencyShutdown()`/the monitoring/event loops, dereferencing `logger_`/`timingController_`, at the instant `initializeComponents()` replaced those members out from under it; `reset()`'s `sleep_for(100ms)` only ever masked this use-after-free window (see the new C40 entry in `docs/v1_release_plan.md`). `joinAndClearThreadHandle`'s self-join guard also unconditionally reset the handle after skipping the join, so `initialize()` called from a system-thread callback ran `~std::thread()` on a still-joinable self-handle — `std::terminate`; the self case was patched to `detach()` instead of `reset()`-ing straight over it. Regression test reruns 10/10 direct + TSan-clean. **Correction (C41):** the sentence above previously claimed `ReinitializeAfterCallbackInitiatedEmergencyShutdown` exercises that self/detach branch — false. Its `initialize()` call runs on the test's main thread; only the cross-thread join branch is regression-tested. The self case is closed by C41's refusal, below.
- C40: `stop()` called from a user event callback ran on `eventProcessingThread_` and joined itself — `std::thread::join` on the calling thread throws, was caught by `stop()`'s own catch, logged as `"Stop failed"`, and escalated to `emergencyShutdown()`: a graceful stop silently became `FATAL_ERROR` instead of `STOPPED`. `reset()` had the analogous shape: `sleep_for(100ms)` after `emergencyShutdown()` was a timing guess, not a synchronization point, before tearing down `logger_`/`timingController_`. Both now reuse `isOnWorkerThread()` and refuse (log an ERROR naming `emergencyShutdown()` as the alternative) when called from a worker thread — `stop()` before its `STOPPING` transition, `reset()` as its first statement — removing the self-join shape rather than guarding it. `reset()`'s sleep is replaced with `{ std::lock_guard<std::mutex> wait(shutdownMutex_); }` (the destructor's existing idiom): a real wait for a **mutex-owning** in-flight teardown, safe from deadlock because the refusal guarantees no worker thread can be the one holding the mutex against us. It does *not* synchronize with a deferred-self-join `emergencyShutdown()` (one running on `eventProcessingThread_`/`monitoringThread_` itself, which `try_lock`-skips the mutex and returns while still unwinding user-code frames) — that gap is closed by a follow-up fix, see below. **Behavior change:** `reset()` now blocks (previously it always slept exactly 100ms) until any concurrent teardown finishes, which can be shorter or longer than 100ms depending on real thread-join time. Regression tests `StopFromEventCallbackIsRefusedWithoutEscalation` and `ResetFromEventCallbackIsRefused`.
- C41: `initialize()` called from an event callback runs on `eventProcessingThread_` itself. C39's self-case `detach()` (see above) left that thread's loop live while `initializeComponents()` replaced `eventPool_`/`eventQueue_`/`logger_`/`timingController_` out from under its own stack — when the callback returned, the resumed loop body dereferenced freed/replaced objects: `eventPool_->deallocateObject(eventPtr)` freed into the wrong pool (heap-use-after-free, ASan-confirmed 5/5 reproductions), and two consumers ended up on one queue. Pre-C39 this was a loud `std::terminate`; C39's detach made it silent. Fix: `eventProcessingLoop()`/`monitoringLoop()` publish their own thread id (`eventThreadId_`/`monitoringThreadId_`, new `std::atomic<std::thread::id>` members) via an RAII guard that clears it on every exit path; new private `isOnWorkerThread()` checks those ids; `initialize()` refuses (logs an error, returns `false`) as its first statement when called from a worker thread, before the C39 joins even run. `joinAndClearThreadHandle`'s self/detach branch, now unreachable from its only caller, is removed rather than kept as untested defense-in-depth. Regression test `InitializeFromEventCallbackIsRefused`: pre-fix 5/5 ASan runs aborted with heap-use-after-free; post-fix green, 420/420 ctest, ASan/TSan clean on `AxonVexSystemTest`.
- `PrecisionTimer(0)`: `max_samples` is now clamped to at least 1 in the constructor. The ring-buffer write path computes `sampleHead_ % max_samples_`; a caller-supplied `0` divided by zero (SIGFPE) on the first eviction instead of failing gracefully.
- C40 follow-up (whole-branch review): `reset()`'s `shutdownMutex_` wait, and the destructor's pre-existing equivalent, synchronize only with a mutex-*owning* teardown — a deferred-self-join `emergencyShutdown()` (running ON `eventProcessingThread_`/`monitoringThread_`, which `try_lock`-skips the mutex and returns while still unwinding user-code frames on that thread) could still be mid-callback when the wait returned, so `reset()`/`~AxonVexSystem()` went on to destroy `logger_`/`timingController_` while that thread was still alive and using them. Both now call `joinAndClearThreadHandle(eventProcessingThread_)` / `joinAndClearThreadHandle(monitoringThread_)` immediately after the wait — safe from self-join because a worker thread cannot reach either path (both refuse via `isOnWorkerThread()` before this point). Also swapped `emergencyShutdown()`'s two self-join checks from reading `eventProcessingThread_->get_id()`/`monitoringThread_->get_id()` (the C36-banned racy shape — reads a handle that `initialize()` concurrently assigns) to comparing against the existing `eventThreadId_`/`monitoringThreadId_` atomics, matching every other self-check in the class.
- Three refusal regression tests (`InitializeFromEventCallbackIsRefused`, `StopFromEventCallbackIsRefusedWithoutEscalation`, `ResetFromEventCallbackIsRefused`) raced their own bookkeeping: the polling main thread woke on `attempted->exchange(true)`, which the callback sets *before* storing its result — a window where the main thread could read a stale/default result and fail spuriously (reproduced 1/36 under 6x parallel load). Each test now gates on a separate `finished` atomic set only after the guarded call returns.
- Corrected wording in `docs/v1_release_plan.md`'s C39/C40 rows and this file's C40 entry that called `reset()`'s `shutdownMutex_` wait "a real synchronization point" without qualification — it synchronizes with mutex-owning teardowns only; see the C40 follow-up entry above for the deferred-self-join gap and its fix.
- C42: `isOnWorkerThread()`'s refusal covered `eventThreadId_`/`monitoringThreadId_` but not `RealTimeScheduler`'s own worker thread — a `ProcessingUnit` task body calling `stop()`/`reset()` self-joined the scheduler thread inside `TimingController::stop()`, the thrown `system_error` was swallowed and silently escalated to `emergencyShutdown()`/`FATAL_ERROR` (C40's exact symptom, from the scheduler's own worker). `RealTimeScheduler` now publishes its own thread id (`schedulerThreadId_`, same `WorkerThreadIdGuard` RAII shape as `eventThreadId_`/`monitoringThreadId_`); `stop()` checks it before touching `schedulerThread_` and defers the join on a self-call instead of self-joining (dropping the `if (!running_) return` early guard so a later `stop()`/`~RealTimeScheduler()` can still absorb the deferred handle, per the `SafetyManager`/`Watchdog` precedent); `AxonVexSystem::isOnWorkerThread()` now also checks the scheduler thread via `TimingController::isOnSchedulerThread()`, so `initialize()`/`stop()`/`reset()` refuse a task exactly like an event/monitoring callback. `~RealTimeScheduler()` gained a joinable-then-join-or-detach decision (`SafetyManager::~SafetyManager()`'s precedent) for the case where the destructor itself runs on the scheduler thread. New `~AxonVexSystem` `@warning`: the destructor cannot refuse a worker-thread call the way `initialize()`/`stop()`/`reset()` can — destroying the system from inside a worker-thread callback is undefined behavior, documented rather than code-enforced. Regression tests `StopFromProcessingUnitTaskIsRefusedWithoutEscalation` (pre-fix: `system_->stop()` from inside a task's `processSync()` swallowed the self-join error, escalated to `FATAL_ERROR`, and a subsequent `stop()` call crashed the process) and `StopFromTaskBodyDefersJoinInsteadOfSelfJoining`.
- C42 follow-up (review finding): `RealTimeScheduler::start()` had the same hazard the fix above closed in `stop()`, one call sooner — after a deferred self-stop, `running_` is false but `schedulerThread_` is still joinable, and `start()` assigned a fresh `std::thread` straight over it with no joinable check: `unique_ptr::operator=` destroying a joinable `std::thread` is `std::terminate`, uncatchable, no log (C39's shape, reintroduced at this layer). `start()` now reads `isOnSchedulerThread()` before touching `schedulerThread_`: joins the leftover handle first when called from a different (external) thread, or refuses outright when called from the scheduler thread itself (a restart from inside the very task whose deferred `stop()` left the handle behind — that thread hasn't unwound out of `schedulerLoop()` yet, so starting a second thread there would run two loops over the same state concurrently; detaching instead would recreate the C41 hazard). Regression test `StartAfterDeferredSelfStopReclaimsHandleAndRunsAgain` (pre-fix: uncaught `std::terminate`; post-fix: green, and the scheduler is confirmed to actually execute tasks again after the restart, not just report `isRunning()`).
- C15: `Path` had four shapes. (a) The three ctors (`Path(const std::string&)`, `Path(const char*)`, `Path(const axonvex_fs::path&)`) each checked a plain `bool initialized_` outside `static_mutex_` before deciding whether to lock and run `initializeDefaultDirs()` — broken double-checked locking: a racing thread could observe `initialized_ == true` while `default_dirs_`'s writes were not yet visible to it. (b) `Path::createConfigPath`/`Path::createLogPath` computed `filename.substr(filename.length() - N)` (N=5 for `.json`, 4 for `.log`) to check the existing extension; for a name shorter than N, `length() - N` underflows `size_t` and `substr()` throws `std::out_of_range` — `Path::createConfigPath("a")` crashed every caller that didn't wrap it in a try/catch. (c) `Path::hasDirectoryTraversal()` substring-matched `".."`/`"./"`/`".\\"` against the whole path string, flagging legitimate names that merely contain those characters (`"my..file.json"`, `"./config/x.json"`) while being no harder to construct a real escape attempt around than an exact-component check. (d) `Path::isInWhitelist()` iterated the static `default_dirs_` map with no lock. Fix: (a) a new `Path::ensureInitialized()` replaces the three ctors' DCLP with a C++11 magic static — the standard's exactly-once-with-synchronization guarantee replaces the broken bool check; the lambda still takes `static_mutex_` around the `initializeDefaultDirs()` call because `default_dirs_` has two post-init writers (`setDefaultDir`, `resetDefaultDirs`, confirmed by grep to be the only ones, both already under `static_mutex_`) that this write must not race. (b) both functions now guard with `filename.length() < N` before calling `substr`. (c) traversal is now component-based: a path is flagged iff one of its components, split manually on both `/` and `\` (not via `axonvex_fs::path`'s own iteration, which only splits on the native separator and would miss a Windows-separator escape attempt on a POSIX build), is exactly `".."`. (d) `isInWhitelist()`'s iteration now takes `static_mutex_`, per (a)'s finding that `default_dirs_` is mutable after init. **Behavior changes:** `createConfigPath`/`createLogPath` no longer throw on short names (the extension is appended instead of underflowing); a path containing `".."` as a substring of a component, or a `./` prefix, is no longer flagged as traversal — a path with a real `".."` component still is, including Windows-separator forms on a POSIX build. Regression tests `PathTest.CreateConfigPathAcceptsShortNames`, `PathTest.TraversalCheckIsComponentBased` (both false-positive and true-positive cases, asserted through the public `isSecure`/`validateSecurity` surface since `hasDirectoryTraversal` is private). (a)'s first-touch initialization race has no deterministic in-suite reproduction — by the time any test runs, an earlier test has already forced the one-time init to complete — so it is verified by inspection plus the full suite (including `PathTest.ThreadSafetyTest`'s 8-thread concurrent `Path` construction) under ThreadSanitizer, not a dedicated race-reproducing test. - C20: `TypeCasterRegistry` keyed its internal map on `typeid(InternalType)` alone, so `registerCaster<float, Float32>` followed by `registerCaster<float, Float64>` silently overwrote the first entry, and a subsequent `getCaster<float, Float32>()` `dynamic_cast`'ed the surviving `Float64` caster to the wrong type and returned a silent `nullptr` — indistinguishable from "never registered". `createServer` built `T data{}` and pushed the default-constructed value, discarding the actual request payload. `ROS2Adapter::registerDefaultCasters()` was an empty body under a doc comment claiming four primitive casters (`float`/`double`/`bool`/`std::string` <-> the matching `std_msgs` type) were pre-registered — an app relying on that claim would compile, run, and silently never receive data.
