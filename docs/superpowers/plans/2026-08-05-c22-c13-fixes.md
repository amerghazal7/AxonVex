# C22 / C13 Defect Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix C22 (MissionPipeline mutates `status_`/`currentElement_` from the scheduler thread and the user control API with zero synchronization; raw non-owned `MissionElement*`; no transition-graph validation) and C13 (the ROS2 plugin is not loadable: `extern "C" inline` factory in a header-only INTERFACE lib produces no `.so` and no dlsym-able symbol; no ABI handshake; PluginManager's dup-name `emplace` silently leaks the instance and the dlopen handle; dlopen flags not explicit).

**Architecture:** C22 gets one `stateMutex_` serializing the control API against the scheduler tick, with the codebase's snapshot-then-dispatch discipline — user code (`MissionElement::onEnter/onExit/execute`) NEVER runs under the lock; the transition graph is validated at `startPipeline()`; the raw-pointer ownership contract is documented. C13 turns the plugin into a real `SHARED` library with a compiled TU exporting non-inline `extern "C"` factories plus an ABI-version symbol; PluginManager verifies the ABI, loads with explicit `RTLD_NOW | RTLD_LOCAL`, and handles duplicate names honestly; a tiny test-fixture plugin `.so` makes the whole load path testable in-tree. ROS 2 Humble is installed at /opt/ros/humble and `BUILD_PLUGINS=ON` in the build cache — but check whether the CURRENT build dir actually found rclcpp (the plugin CMake `return()`s quietly if not); if it didn't, the test-fixture plugin still verifies the loader end-to-end and the ros2 `.so` gets an `nm -D` symbol verification recorded instead of a dlopen test.

**Tech Stack:** C++14, GoogleTest/CTest, dlopen/dlsym (Linux), CMake MODULE/SHARED targets, ASan/TSan.

## Global Constraints

- **C++14 strictly.** No C++17-isms.
- **Zero-warning policy.** No new dependencies (rclcpp is already a declared plugin dependency).
- **Never invoke user callbacks while holding a lock** — MissionElement hooks are user code; snapshot under the lock, release, then dispatch (5 prior defects in this class: C12/C18/C34…).
- **No sleep-based test synchronization** — poll atomics against steady_clock deadlines; separate gate/finished atomics (finished stored AFTER the call).
- **TSan mandatory for Task 1** (new lock vs scheduler thread); **ASan mandatory for Task 2** (the pre-fix dup-name bug is a leak — LSan sees it).
- **Parallel-load gate** for any lifecycle/threaded test: 6 concurrent processes × ≥6 repeats, all green.
- **Platform rule:** a platform that can't do the operation returns an error — the non-Linux `makePosixLoader()` returning an empty LoaderFn is existing honest behavior; don't change it.
- Build/test commands (dirs configured; NEVER run conan or cmake configure — EXCEPTION for Task 2: adding new CMake targets requires re-running the existing configure ONCE per build dir with the SAME cached arguments; do it as `cmake build` (no -D flags — the cache carries them) and say so in the report):
  - `cmake --build build -j$(nproc)` then `ctest --test-dir build --output-on-failure`
  - ASan: `cmake --build build-asan -j$(nproc)` + filtered ctest; TSan: `setarch $(uname -m) -R ctest --test-dir build-tsan ...`
  - Known flakes (rerun once): `TimingControllerTest.SchedulerPauseAndResume`, `PrecisionTimerTest.PerformanceTest`; TSan perf tests.
- `clang-format -i` touched files. Defect ID in commit messages. Plan §3 rows: SYMBOL refs + Status paragraph + CHANGELOG (behavior/breaking changes labeled), same commit.

### Task 1: C22 — MissionPipeline synchronization, ownership contract, transition-graph validation

**Files:**
- Modify: `src/libs/axonvex_core/include/axonvex_core/missionPipeline.hpp` (the whole control API + `processSync` path; members `status_`, `currentElement_`, `elements_`, `transitions_`, `startElementName_`)
- Test: `tests/core/missionTest.cpp` (exists)

**Interfaces:**
- Consumes: `MissionElement` (missionElement.hpp — read its hook set: `onEnter/onExit/execute/reset`, `name()`); `ProcessingUnit::processSync` runs on the scheduler thread.
- Produces: no signature changes to the control API. New contracts: (1) control methods (`startPipeline/abort/pause/resume/restart`) are safe to call from any non-worker thread concurrently with the scheduler tick; (2) `MissionElement*` registered via `addElement` are NON-OWNED with a stable-reference contract — caller must keep them alive until the pipeline is destroyed (document at `addElement`); (3) `startPipeline()` validates the transition graph first (every transition's `from`/`to` names an added element; start element exists) and sets `Failed` + surfaces which reference is dangling via the unit's existing error path if invalid.

**Defect (plan §3 row C22):** `status_` and `currentElement_` are plain members written by the public control API (any thread) and read/written by `processSync` (scheduler thread) with no synchronization — torn/racy state on a safety-relevant control object. `elements_`/`transitions_` maps are likewise mutated unlocked. Raw `MissionElement*` with no documented ownership. No validation that transitions reference real elements (a typo'd transition is discovered only as a wedged pipeline at runtime).

**Design constraints (bind the implementation):**
- One `mutable std::mutex stateMutex_` guards `status_`, `currentElement_`, `elements_`, `transitions_`, `startElementName_`.
- `MissionElement` hooks are USER CODE: every call to `onEnter/onExit/execute/reset` happens with the mutex RELEASED, on a pointer snapshotted under the lock. Where a state change and a hook must appear atomic to observers (e.g. `abort()`'s onExit + status flip), do: lock → capture element + apply state flip → unlock → invoke hook. A hook may call back into the control API — re-entrancy must not deadlock: NEVER hold the mutex across a hook; the mutex stays non-recursive.
- `processSync()` (scheduler thread — RT path): the lock is held only for the state decision/snapshot, never across `execute()`. Add the RT-ceiling comment the project requires: name the cost (one uncontended mutex per tick at mission-rate frequency) and the upgrade path (atomics + SPSC command queue if a benchmark ever shows contention).
- Graph validation: private `bool validateGraph(std::string& firstError) const` (called under the lock from `startPipeline`); checks the start element exists and every `transitions_` from/to key names an element in `elements_`. On failure: `status_ = Failed` and surface `firstError` through ProcessingUnit's existing error-reporting mechanism (read what exists — `setError` or similar; use it).

### Task 2: C13 — ROS2 plugin not loadable; PluginManager dup-name leak; ABI handshake

- Create: `plugins/axonvex_ros2/src/ros2Plugin.cpp` — the ONE TU: non-inline `extern "C"` definitions of `axonvex_create_plugin`, `axonvex_destroy_plugin`, and the new ABI symbol
- Modify: `plugins/axonvex_ros2/include/axonvex_ros2/ros2Plugin.hpp` — factory definitions REMOVED from the header
- Modify: `src/libs/axonvex_plugins/include/axonvex_plugins/pluginInterface.hpp` — add the ABI version constant (`AXONVEX_PLUGIN_ABI_VERSION`, value 1, C-linkage-friendly) + doc block: every plugin must export `extern "C" uint32_t axonvex_plugin_abi_version()` returning it
- Modify: `src/libs/axonvex_plugins/include/axonvex_plugins/pluginManager.hpp`:

  - Read the REST of the file before editing (unload/destructor paths — do stored handles get dlclosed on destruction? Fix only if it's a leak within C13's scope, i.e. LoadedPlugin teardown; otherwise note it)
- Create: test-fixture plugins — `tests/plugins/fixture/testPlugin.cpp` + CMake `MODULE` targets: `axonvex_test_plugin` (normal) and `axonvex_test_plugin_oldabi` (same TU compiled with a `-D` override reporting a WRONG abi version)

**Interfaces:**
- Consumes: nothing from Task 1.
- Produces: BREAKING for out-of-tree plugins: the loader now REQUIRES `axonvex_plugin_abi_version` (a plugin without it fails to load with a reason) — label in CHANGELOG. `PluginManager::lastError()`. The ros2 plugin becomes a real `.so`.

**Defect (plan §3 row C13):** `extern "C" inline` factory functions in a header of an INTERFACE (header-only) library: no TU compiles them, no `.so` is produced, nothing is dlsym-able — the plugin cannot be loaded by the very PluginManager designed for it.
